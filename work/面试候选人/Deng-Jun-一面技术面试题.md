# 邓均一面技术面试题

## 1. 面试目标

该候选人履历偏高级技术经理、架构负责人，经历覆盖 Java、服务治理、推荐算法、大数据、Kafka、云原生、RAG、多租户平台。一面建议重点考察三件事：

- 技术真实性：是否真的主导过简历中的关键项目，而不是只参与或管理。
- 架构深度：是否能从业务目标推导架构方案，并讲清核心取舍。
- 一线落地能力：是否仍具备代码、故障处理、性能优化和工程细节能力。

不建议把时间主要花在普通八股题上。更有效的方式是抓住简历中的重点项目连续深挖。

## 2. 建议面试流程

总时长可按 60 分钟设计：

1. 5 分钟：候选人自我介绍，要求聚焦最近 3 年最核心项目。
2. 15 分钟：选择一个最近项目画架构图，追问关键链路。
3. 20 分钟：围绕推荐系统、服务治理、消息一致性、RAG 等方向深挖。
4. 15 分钟：现场系统设计或代码题。
5. 5 分钟：线上故障、技术决策、团队协作和候选人提问。

建议开场问题：

> 请你选择最近 3 年最熟悉、最能代表你技术能力的一个项目，画一下核心架构图，并说明你本人负责的部分。

## 3. 核心技术问题

### 3.1 推荐系统与流量策略

简历依据：主导算法推荐架构云端迁移，人均分发提升 200%+，广告 ARPU 超过 50%+。

可问问题：

- 你们推荐系统的整体架构是什么？召回、粗排、精排、重排分别怎么做？
- 用户画像、商品特征、实时行为特征分别如何生产和更新？
- 人均分发提升 200%+ 的指标定义是什么？分母、分子分别是什么？
- 如何排除流量变化、活动、季节因素对指标的影响？
- 广告 ARPU 提升主要来自推荐策略、竞价策略、流量分配还是广告库存变化？
- 如何做 A/B 实验？实验分桶、流量隔离、显著性判断怎么处理？
- 冷启动用户、冷启动商品怎么处理？
- 推荐服务线上延迟预算是多少？超时、降级、兜底策略是什么？
- 如果模型效果离线很好，但线上转化变差，你会怎么排查？

重点追问：

- 离线训练、在线推理、实时特征链路如何衔接？
- 模型效果如何评估？CTR、CVR、GMV、留存、ARPU 是否存在冲突？
- 线上排序策略如何与业务规则结合，例如广告、库存、价格、商家权重？

好信号：

- 能讲清指标口径、实验设计、特征链路、召回排序分层、线上延迟和降级。

风险信号：

- 只说算法优化、模型升级，讲不清指标、数据链路和线上策略。

### 3.2 RAG 与多模态图文匹配 Agent

简历依据：基于 RAG 的多模态图文匹配 Agent 系统，技能中包含 Faiss、RAG、语义检索、Dify。

可问问题：

- 这个 RAG 系统解决的具体业务问题是什么？
- 文本、图片分别如何向量化？用的是什么 embedding 模型？
- 图片和文本是在同一个向量空间检索，还是分开召回后融合？
- Faiss 索引怎么选型？Flat、IVF、HNSW、PQ 分别适合什么场景？
- 向量库如何更新？增量更新、删除、重建索引怎么做？
- 如何评估图文匹配效果？Precision、Recall、NDCG、人工标注如何结合？
- RAG 里如何减少幻觉？上下文截断、rerank、引用来源、置信度怎么设计？
- Agent 的工具调用边界怎么控制？如何避免无限循环或错误调用？

重点追问：

- 数据集如何构建？正负样本如何产生？
- 多模态检索召回不足时，如何做 query rewrite 或 rerank？
- 如果向量召回结果相关性差，排查路径是什么？

好信号：

- 能讲 embedding、索引、召回评估、rerank、数据质量和线上反馈闭环。

风险信号：

- 只会说大模型加知识库，不懂召回、索引和评估。

### 3.3 服务化框架、熔断、限流、灰度

简历依据：在货拉拉主导泛服务化调用框架，设计熔断、降级限流、注册中心、高可用、灰度发布能力。

可问问题：

- 泛服务化调用框架的核心抽象是什么？接口、路由、协议、序列化如何设计？
- 注册中心如何保证高可用？服务发现缓存失效怎么办？
- 熔断、限流、降级分别解决什么问题？触发条件怎么配置？
- 限流是单机限流还是分布式限流？令牌桶和漏桶有什么差异？
- 全链路灰度如何传递灰度标识？HTTP、RPC、MQ 链路如何保持一致？
- 如果灰度流量进入了非灰度实例，如何发现和阻断？
- 框架升级如何兼容老业务？如何做 SDK 版本治理？
- 服务治理指标有哪些？成功率、P99、熔断次数、限流次数如何采集？

重点追问：

- 灰度规则冲突时如何处理优先级？
- MQ 异步链路如何传递灰度上下文？
- 限流策略误伤核心客户时如何快速恢复？

好信号：

- 能讲清调用链路、路由规则、上下文透传、灰度污染、指标治理。

风险信号：

- 只停留在 Spring Cloud 组件名，讲不出框架内部机制。

### 3.4 消息可靠性与最终一致性

简历依据：飞书 eLearning 中设计基于本地事务的消息可靠性传输，两阶段提交能力，类 RocketMQ 事务消息。

可问问题：

- 你们为什么不用 RocketMQ 原生事务消息，而是自己实现？
- 本地事务和消息发送如何保证一致性？
- 消息表是怎么设计的？状态机有哪些？
- 发送成功但业务提交失败怎么办？业务提交成功但消息发送失败怎么办？
- 消息重复消费如何处理？幂等键如何设计？
- 延时消息基于内存实现，服务重启后怎么恢复？
- 消息积压如何监控和处理？
- 最终一致性场景下，用户可见的不一致如何兜底？

重点追问：

- 是否采用 outbox 模式？
- 补偿任务如何避免重复补偿？
- 如何判断消息已经不可恢复，需要进入死信或人工处理？

好信号：

- 能讲 outbox、状态补偿、幂等、重试、死信、可观测性。

风险信号：

- 把事务消息简化成加重试，忽略幂等和异常状态。

### 3.5 大文件上传、加密、对象存储

简历依据：支持大文件大于 10G 断点续传、文件无损压缩、转码、图片裁剪，AES CBC 分段加密，对接对象存储和多 CDN。

可问问题：

- 大文件断点续传的分片协议怎么设计？
- 分片上传如何校验完整性？MD5、SHA、分片 hash、全量 hash 如何取舍？
- 秒传和分片复用如何实现？如何避免不同用户文件权限串用？
- AES CBC 分段加密为什么这么设计？IV 如何生成和保存？
- CBC 分段加密如何支持流式处理和断点续传？
- 对象存储里元数据如何设计？文件、分片、用户授权之间是什么关系？
- CDN 访问如何做鉴权？签名 URL、过期时间、防盗链怎么处理？
- 文件转码、压缩、裁剪是同步还是异步？失败如何重试？

重点追问：

- 分片大小如何确定？
- 上传过程中服务端是否落盘？如果不落盘如何加密和校验？
- 分片复用和安全隔离之间如何平衡？

好信号：

- 能讲分片元数据、完整性校验、权限隔离、加密模式风险。

风险信号：

- 对加密和对象存储只讲概念，无法解释边界条件。

### 3.6 Kafka、流式数据和可观测性平台

简历依据：Metrics Pipeline、Kafka、Kafka Streaming、Kafka Connect、Grafana、多租户日志流式分析平台。

可问问题：

- Metrics Pipeline 的数据模型怎么设计？metric name、tag、timestamp、value 怎么存？
- 高基数 tag 会带来什么问题？如何限制或治理？
- Kafka topic、partition、key 如何设计？
- 如何保证消费顺序？什么场景需要顺序？
- Kafka 消费延迟升高，你会从哪些维度排查？
- At least once、at most once、exactly once 分别如何实现或接近？
- Kafka Connect 适合什么场景？和自己写 consumer 有什么区别？
- 指标平台如何支持多租户隔离？

重点追问：

- 消费端如何做反压？
- 指标写入失败如何补偿？
- 日志和指标的数据保留策略如何设计？

好信号：

### 3.7 数据库与高吞吐写入

## 5. 现场代码题

### 题目：实现一个滑动窗口限流器

要求：

```java
boolean allow(String key, int limit, long windowMillis)
```

功能要求：

- 同一个 key 在窗口内最多允许 limit 次。
- 考虑并发安全。
- 说明单机版如何扩展到 Redis 分布式版。

可接受方向：

- 单机版可以用 `ConcurrentHashMap<String, Deque<Long>>`。
- 每次请求清理窗口外时间戳。
- 对同一个 key 做细粒度同步，避免全局锁。
- Redis 版可以用 ZSet，score 使用时间戳。

追问：

- 固定窗口有什么问题？
- 滑动日志和滑动计数器有什么区别？
- Redis ZSet 版如何实现？
- 如何处理 Redis 时间和应用机器时间不一致？
- 高并发下 ZSet 热 key 如何优化？

考察点：

- 并发安全。
- 边界条件。
- 数据结构选择。
- 分布式一致性和性能取舍。
- 候选人是否仍有一线编码能力。

## 7. 一面评分维度

建议按 5 分制评分：

| 维度 | 说明 | 评分关注点 |
| --- | --- | --- |
| 技术真实性 | 是否真实主导过项目 | 能否讲清关键链路、个人贡献、指标口径 |
| 架构能力 | 是否能设计复杂系统 | 模块边界、扩展性、可用性、成本和取舍 |
| 工程落地 | 是否关注生产可用 | 异常、幂等、监控、灰度、回滚、性能 |
| 一线编码能力 | 是否仍能写核心代码 | 数据结构、并发、边界条件、代码表达 |
| 数据意识 | 是否能证明业务收益 | 指标定义、A/B 实验、归因、显著性 |
| 技术管理 | 是否能带团队交付 | 质量机制、协作流程、风险控制、人员培养 |

建议结论分类：

- 强通过：能深讲 2 到 3 个核心项目，细节扎实，架构取舍清晰，仍具备一线判断力。
- 通过：项目经验真实，部分深度略弱，但能胜任架构或技术负责人角色。
- 待定：管理表达较强，但关键技术细节不稳，需要二面继续验证。
- 不通过：指标和项目描述经不起追问，无法解释核心方案和异常处理。

## 8. 推荐面试策略

这位候选人履历很强，一面不要平均用力。建议重点抓四条线：

1. 推荐系统收益是否真实：追问指标口径、实验设计、线上链路。
2. 服务化灰度是否真做过：追问上下文透传、路由隔离、灰度污染。
3. 消息一致性是否懂落地：追问 outbox、幂等、补偿、死信。
4. RAG 检索是否有工程深度：追问 embedding、Faiss、评估、rerank。

如果这四条线能答深，候选人的技术含金量基本较高；如果只能停留在宏观描述，则更可能偏项目管理或包装型架构经历。
