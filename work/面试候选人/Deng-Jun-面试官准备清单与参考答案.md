# 邓均一面面试官准备清单与参考答案

## 1. 使用方式

这份文档不是让面试官背答案，而是帮你判断候选人的回答是否靠谱。

你面试时可以按这个节奏使用：

1. 先让候选人讲项目和画架构图。
2. 选择 2 到 3 个你想重点验证的方向深挖。
3. 候选人回答后，对照本文的“满意回答应包含”判断深度。
4. 如果你听不懂某个细节，就追问“为什么这么设计”“这个方案的缺点是什么”“线上出问题怎么处理”。

核心原则：

- 不要求候选人和本文答案完全一致。
- 满意答案一定会包含场景、指标、架构、异常、取舍。
- 风险答案通常只有名词、组件、宏观描述，没有边界条件。

## 2. 面试官需要提前准备的知识清单

### 2.1 必须掌握

这些概念建议面试前至少知道基本含义：

- 推荐系统：召回、粗排、精排、重排、用户画像、特征、A/B 实验。
- 服务治理：注册发现、熔断、限流、降级、灰度、链路追踪。
- 消息一致性：本地事务、消息表、outbox、幂等、补偿、死信队列。
- Kafka：topic、partition、consumer group、offset、lag、消息顺序。
- MySQL 高并发写入：批量写入、索引成本、锁、binlog、redo log、分库分表。
- RAG：embedding、向量检索、rerank、上下文拼接、幻觉控制。
- 文件系统：分片上传、断点续传、对象存储、CDN 鉴权、加密。
- 分布式任务：主备、分片、锁、租约、幂等、重复执行。

### 2.2 不需要掌握到专家级

这些内容你只需要知道判断方向，不需要和候选人硬拼细节：

- 具体模型结构，比如深度推荐模型内部网络层。
- Faiss 每种索引的底层实现。
- Kafka exactly once 的源码级实现。
- AES 加密算法数学细节。
- Kubernetes 或 Service Mesh 的完整架构。

### 2.3 你最应该记住的追问句式

- 这个指标具体怎么定义？
- 这个方案的瓶颈在哪里？
- 如果这个模块挂了，会怎么降级？
- 如何证明收益是这个方案带来的？
- 如果数据重复、延迟、丢失，你怎么处理？
- 你本人负责的是哪一部分？
- 有没有线上事故？最后怎么修复？
- 如果重新做一次，你会改哪里？

## 3. 推荐系统方向

### 3.1 你需要知道的基础

推荐系统通常不是一个模型，而是一条链路：

1. 收集用户行为，例如点击、收藏、购买、停留。
2. 生成用户画像和商品特征。
3. 从海量商品中召回一批候选商品。
4. 用模型或规则排序。
5. 加上业务规则重排，例如广告、库存、商家权重、多样性。
6. 通过 A/B 实验验证效果。

常见指标：

- CTR：点击率。
- CVR：转化率。
- GMV：交易额。
- ARPU：人均收入。
- 曝光、点击、下单、成交、留存。

### 3.2 可问问题

> 你简历里写人均分发提升 200%+，广告 ARPU 超过 50%+，这个指标具体怎么定义？你们如何证明提升来自推荐系统？

### 3.3 满意回答应包含

一个满意回答大致应该是：

> 我们先明确指标口径。人均分发指的是单位活跃用户每天收到的有效商品分发量，不是单纯曝光量。广告 ARPU 是广告收入除以活跃用户数。为了证明收益，我们做了 A/B 实验，按用户维度稳定分桶，实验组走新推荐链路，对照组保持旧策略。观察 CTR、CVR、ARPU、留存等指标，同时排除大促、流量来源变化、类目变化的影响。技术上我们做了召回扩展、实时行为特征接入、排序模型优化和重排策略调整。线上有超时预算，如果实时特征或模型服务超时，会降级到缓存推荐、热门商品或规则兜底。

你可以听这些关键点：

- 是否讲清指标口径。
- 是否提到 A/B 实验。
- 是否区分召回、排序、重排。
- 是否提到线上延迟和降级。
- 是否知道收益归因不能只看上线前后对比。

### 3.4 风险回答

下面这类回答要警惕：

> 我们主要是换了一个深度学习模型，所以效果提升很多。

问题在于：

- 没有指标定义。
- 没有实验设计。
- 没有解释线上链路。
- 没有说明他本人贡献。

## 4. RAG 与向量检索方向

### 4.1 你需要知道的基础

RAG 可以理解为“先检索资料，再让大模型基于资料回答”。

典型链路：

1. 把文本或图片转成向量，也就是 embedding。
2. 存入向量库，例如 Faiss。
3. 用户输入 query 后，也转成向量。
4. 用向量相似度召回候选内容。
5. 可选：用 rerank 模型重新排序。
6. 把最相关内容拼给大模型生成答案。

多模态图文匹配通常要处理：

- 图片向量。
- 文本向量。
- 图文是否在同一向量空间。
- 召回准确率。
- 人工标注和效果评估。

### 4.2 可问问题

> 你们的多模态图文匹配 RAG 系统，图片和文本是怎么被检索到一起的？如何评估效果？

### 4.3 满意回答应包含

一个满意回答大致应该是：

> 我们先用多模态 embedding 模型把图片和文本映射到同一语义空间，或者分别召回后再融合。图片侧会抽取视觉特征，文本侧会处理标题、描述、类目、属性等信息。检索层用 Faiss 做向量索引，根据数据量和延迟要求选择索引类型。召回后会做 rerank，结合类目、属性匹配、相似度分数和业务规则。评估上不能只看相似度，要用人工标注集计算 Precision、Recall、NDCG，并且看线上点击、转化或人工审核通过率。RAG 生成时还要控制上下文来源，避免模型编造。

你可以听这些关键点：

- 是否知道 embedding 是核心。
- 是否知道向量检索后还需要 rerank。
- 是否能讲评估指标。
- 是否知道 RAG 可能出现幻觉。
- 是否知道索引更新和删除是工程问题。

### 4.4 风险回答

下面这类回答要警惕：

> 我们把图片和文字丢给大模型，大模型会判断是否匹配。

问题在于：

- 没有检索链路。
- 没有向量索引。
- 没有效果评估。
- 成本和延迟不可控。

## 5. 服务治理与全链路灰度方向

### 5.1 你需要知道的基础

服务治理主要解决微服务系统中的稳定性和可控性问题：

- 注册发现：服务实例如何被找到。
- 熔断：下游持续失败时，暂时不再调用。
- 限流：限制请求量，保护系统。
- 降级：非核心能力失败时，返回兜底结果。
- 灰度：让少量用户或租户先走新版本。
- 链路追踪：知道一次请求经过哪些服务。

全链路灰度的难点是：

- 灰度标识要从入口一路传到所有下游。
- HTTP、RPC、MQ 都要传递灰度上下文。
- 灰度流量不能错误进入普通实例。
- 普通流量也不能误入灰度实例。

### 5.2 可问问题

> 全链路灰度具体怎么做？如果一个灰度请求经过 HTTP、RPC、MQ，怎么保证后续链路都走灰度环境？

### 5.3 满意回答应包含

一个满意回答大致应该是：

> 入口网关根据用户、租户、版本、请求头等规则判断是否命中灰度，并写入灰度上下文，例如 header 或 trace context。后续 RPC 调用由框架自动透传该标识，服务发现或负载均衡根据标识选择灰度实例。MQ 场景需要把灰度标识写入 message header，消费者根据标识路由到对应处理逻辑或实例。为了避免灰度污染，需要监控灰度请求是否调用了非灰度实例，也要有兜底规则和一键回滚能力。灰度规则还要考虑优先级、缓存、动态刷新和审计。

你可以听这些关键点：

- 是否提到入口打标。
- 是否提到上下文透传。
- 是否覆盖 MQ 异步链路。
- 是否提到灰度污染。
- 是否提到监控和回滚。

### 5.4 风险回答

下面这类回答要警惕：

> 灰度就是部署两套服务，然后在网关配一点流量过去。

问题在于：

- 只覆盖入口流量。
- 没有全链路上下文。
- 没有 MQ 场景。
- 没有污染检测和回滚。

## 6. 消息一致性方向

### 6.1 你需要知道的基础

常见问题：

- 数据库事务成功了，但消息没发出去。
- 消息发出去了，但数据库事务失败。
- 消费者处理成功了，但确认消息失败，导致重复消费。

常见方案：

- 本地消息表，也叫 outbox。
- 业务数据和消息记录放在同一个数据库事务里提交。
- 后台任务扫描待发送消息。
- 发送失败重试。
- 消费端做幂等。
- 多次失败进入死信或人工处理。

### 6.2 可问问题

> 你们基于本地事务做消息可靠投递，具体如何保证业务数据和消息最终一致？

### 6.3 满意回答应包含

一个满意回答大致应该是：

> 我们不会在业务事务里直接依赖消息发送成功，而是把业务数据和消息记录写入同一个本地事务。事务提交后，消息表里会有待发送记录，由异步发送器投递到 MQ。发送成功后更新状态。如果发送失败，会按次数和时间间隔重试，超过阈值进入异常状态或死信。消费端必须做幂等，例如使用业务唯一键或消息 ID 记录处理状态。这样即使服务重启、MQ 短暂不可用，也能通过补偿任务恢复最终一致。

你可以听这些关键点：

- 是否提到本地消息表。
- 是否提到同一个数据库事务。
- 是否提到异步补偿。
- 是否提到消费幂等。
- 是否提到死信或人工介入。

### 6.4 风险回答

下面这类回答要警惕：

> 失败了就重试，多重试几次就可以了。

问题在于：

- 没有解决事务边界。
- 没有消息状态机。
- 没有幂等。
- 没有死信和补偿。

## 7. Kafka 与流式数据方向

### 7.1 你需要知道的基础

Kafka 的几个核心概念：

- topic：消息主题。
- partition：分区，决定并行度和顺序范围。
- consumer group：消费者组，同一组内分摊消费。
- offset：消费进度。
- lag：积压量，也就是生产速度大于消费速度时的落后程度。

Kafka 不是天然保证全局顺序。它只保证同一个 partition 内有序。

### 7.2 可问问题

> Kafka 消费延迟突然升高，你会怎么排查？

### 7.3 满意回答应包含

一个满意回答大致应该是：

> 我会先看 lag 是所有 partition 都升高，还是部分 partition 升高。如果是部分 partition，可能是 key 分布不均或单条消息处理太慢。如果全部升高，要看生产流量是否突增、消费者实例是否减少、消费逻辑是否变慢、下游数据库或外部服务是否变慢。还要看消费者是否频繁 rebalance、是否有异常重试。处理上可以临时扩容消费者，但前提是 partition 数足够；也可以优化批量处理、隔离慢消息、降级下游调用，必要时限流生产端。

你可以听这些关键点：

- 是否先看 lag。
- 是否区分全部积压和局部积压。
- 是否知道 partition 限制并行度。
- 是否关注下游处理能力。
- 是否提到 rebalance 和慢消息。

### 7.4 风险回答

下面这类回答要警惕：

> 加机器就行。

问题在于：

- partition 不够时加消费者无效。
- 没有定位生产、消费、下游瓶颈。
- 没有处理慢消息。

## 8. MySQL 高吞吐写入与财务对账方向

### 8.1 你需要知道的基础

MySQL 写入性能受这些因素影响：

- 单条写入还是批量写入。
- 索引数量，索引越多写入成本越高。
- 唯一约束冲突。
- 事务大小。
- 磁盘和 redo log。
- binlog。
- 锁竞争。
- 是否分库分表。

财务金额不能用 float 或 double，因为二进制浮点会有精度误差，应该使用整数分或 BigDecimal。

### 8.2 可问问题

> 你简历里写数据库写入 20k/s，这个数据是怎么做到的？表结构和写入策略怎么设计？

### 8.3 满意回答应包含

一个满意回答大致应该是：

> 20k/s 首先要说明是峰值还是平均值，是单库单表还是分库分表。一般我们会通过批量写入、减少非必要索引、按业务维度分表、异步削峰来提升吞吐。对账数据要有业务唯一键，保证重复导入或重跑时幂等。金额使用整数分或 BigDecimal。对账不能只按实时数据判断，需要考虑上下游延迟，所以会设计时间窗口和多轮复核，避免误报。差异结果要能追溯到原始流水，并支持修复闭环。

你可以听这些关键点：

- 是否说明 20k/s 口径。
- 是否提到批量写入。
- 是否提到索引成本。
- 是否提到幂等。
- 是否提到金额精度。
- 是否提到上下游延迟和误报。

### 8.4 风险回答

下面这类回答要警惕：

> 我们就是优化 SQL，加了索引，所以写入很快。

问题在于：

- 写入场景加索引不一定更快。
- 没有吞吐口径。
- 没有幂等和对账逻辑。

## 9. 大文件上传与对象存储方向

### 9.1 你需要知道的基础

大文件上传常见做法：

1. 客户端把文件切成多个分片。
2. 每个分片独立上传。
3. 服务端记录上传进度。
4. 上传中断后，只补传缺失分片。
5. 所有分片完成后合并或提交对象存储合并。
6. 用 hash 校验文件完整性。

对象存储通常用于存文件本体，数据库保存文件元数据。

### 9.2 可问问题

> 大于 10G 的文件断点续传，你们的分片、校验、权限和加密是怎么设计的？

### 9.3 满意回答应包含

一个满意回答大致应该是：

> 客户端会先发起上传任务，服务端生成 uploadId，并记录文件大小、分片大小、分片数量、用户权限和文件 hash。每个分片上传后记录状态和分片 hash。断点续传时查询已完成分片，只上传缺失部分。完整性上可以校验分片 hash 和最终文件 hash。对象存储保存文件或分片，数据库保存元数据。权限上不能只按文件 hash 秒传给所有用户，必须建立用户和文件的授权关系。加密如果使用分段加密，需要每段有明确 IV 或派生方式，并保证解密顺序和完整性。

你可以听这些关键点：

- 是否有 uploadId。
- 是否有分片元数据。
- 是否有 hash 校验。
- 是否区分文件存储和权限关系。
- 是否知道秒传有权限风险。
- 是否能说清加密和断点续传的关系。

### 9.4 风险回答

下面这类回答要警惕：

> 前端分片传，后端拼起来就行。

问题在于：

- 没有断点状态。
- 没有完整性校验。
- 没有权限控制。
- 没有对象存储和加密细节。

## 10. 分布式定时任务方向

### 10.1 你需要知道的基础

分布式定时任务常见模式：

- 主备模式：只有主节点执行任务，备节点等待接管。
- 分片模式：多个节点各自执行一部分任务。

关键问题：

- 如何选主。
- 主节点挂了如何切换。
- 如何避免两个节点同时执行。
- 任务重复执行怎么办。
- 长任务执行中节点挂了怎么办。
- 多时区和夏令时怎么处理。

### 10.2 可问问题

> Active-Standby 分布式 Timer 怎么避免脑裂和重复执行？

### 10.3 满意回答应包含

一个满意回答大致应该是：

> 主备模式下需要一个可靠的协调机制，例如数据库锁、Redis 锁、Zookeeper 或类似租约机制。主节点定期续约，备节点发现租约过期后才接管。为了避免脑裂，锁要有 owner、过期时间和 fencing token，执行任务前校验自己仍然持有有效租约。即使这样，也不能完全假设任务只执行一次，所以业务侧要做幂等。长任务要记录执行状态，节点挂掉后可以恢复或重新调度。多时区任务最好统一存 UTC，同时保存用户时区，用可靠时间库处理夏令时。

你可以听这些关键点：

- 是否提到锁或租约。
- 是否提到续约。
- 是否提到脑裂。
- 是否提到幂等。
- 是否提到任务状态。
- 是否知道多时区不能简单加减小时。

### 10.4 风险回答

下面这类回答要警惕：

> 我们部署两个节点，一个主一个备，主挂了备就执行。

问题在于：

- 没有解释如何判断主挂了。
- 没有防脑裂。
- 没有重复执行处理。

## 11. 滑动窗口限流代码题参考答案

### 11.1 你需要知道的基础

限流是为了保护系统。

常见算法：

- 固定窗口：实现简单，但窗口边界可能瞬间放过两倍流量。
- 滑动日志：记录每次请求时间，精确但内存成本较高。
- 滑动窗口计数：把窗口拆成多个小格，精度和成本折中。
- 令牌桶：允许一定突发流量。
- 漏桶：让请求以固定速度流出。

### 11.2 可问问题

> 请实现一个单机版滑动窗口限流器，并说明如何扩展成 Redis 分布式版。

### 11.3 满意回答应包含

单机版思路：

```java
public class SlidingWindowLimiter {
    private final ConcurrentHashMap<String, Deque<Long>> records = new ConcurrentHashMap<>();

    public boolean allow(String key, int limit, long windowMillis) {
        long now = System.currentTimeMillis();
        Deque<Long> queue = records.computeIfAbsent(key, k -> new ArrayDeque<Long>());
        synchronized (queue) {
            while (!queue.isEmpty() && now - queue.peekFirst() >= windowMillis) {
                queue.pollFirst();
            }
            if (queue.size() >= limit) {
                return false;
            }
            queue.addLast(now);
            return true;
        }
    }
}
```

这个答案的优点：

- 用 `ConcurrentHashMap` 管理不同 key。
- 对单个 key 的队列加锁，避免全局锁。
- 每次请求清理窗口外的时间戳。
- 逻辑简单，适合说明滑动日志算法。

可以继续追问：

- key 很多时，空队列如何清理？
- 单个热 key 并发很高时怎么办？
- 系统时间回拨怎么办？
- limit 或 windowMillis 非法时如何处理？

Redis 分布式版满意回答：

> 可以用 Redis ZSet 实现。key 是限流对象，score 和 member 都可以包含当前时间戳加随机值。每次请求先删除窗口外数据，再统计窗口内数量，如果小于 limit 就写入当前请求并允许，否则拒绝。这个过程要用 Lua 脚本保证原子性。时间最好使用 Redis 服务器时间，避免应用机器时钟不一致。还要给 key 设置过期时间，防止内存泄漏。

你可以听这些关键点：

- 是否用 ZSet。
- 是否删除窗口外数据。
- 是否统计窗口内数量。
- 是否用 Lua 保证原子性。
- 是否使用 Redis 时间。
- 是否设置过期时间。

## 12. 通用判断模板

当候选人回答一个复杂项目时，你可以按这个模板判断：

| 判断点 | 满意表现 | 风险表现 |
| --- | --- | --- |
| 背景 | 说得清业务问题和技术目标 | 只讲用了什么组件 |
| 指标 | 有明确口径和前后对比方式 | 只有提升百分比 |
| 架构 | 能画出核心链路和模块边界 | 架构图只有大框 |
| 细节 | 能讲数据结构、状态机、异常处理 | 遇到细节开始泛化 |
| 取舍 | 能说明为什么不用另一个方案 | 认为方案没有缺点 |
| 线上 | 有监控、降级、回滚、复盘 | 默认系统正常运行 |
| 个人贡献 | 明确说自己设计或实现哪部分 | 一直说我们，没有个人边界 |

## 14. 最推荐的面试组合

如果你时间有限，建议只准备并执行下面这组：

1. 推荐系统收益：验证业务指标和技术真实性。
