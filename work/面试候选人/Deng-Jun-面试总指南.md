# 邓均面试总指南

## 1. 使用说明

这份指南由三份材料合并整理而来：

- `Deng-Jun-简历结构化整理.md`
- `Deng-Jun-一面技术面试题.md`
- `Deng-Jun-面试官准备清单与参考答案.md`

它不是让面试官背题，而是帮助面试官在有限时间内判断三件事：

- 技术真实性：候选人是否真实主导过简历中的关键项目。
- 架构深度：候选人是否能从业务目标推导架构方案，并讲清取舍。
- 交付能力：候选人是否能把复杂项目从目标、资源、风险、上线、复盘完整推进下来。

使用原则：

- 不要平均覆盖所有项目，重点抓 2 到 4 条主线连续深挖。
- 不要只问组件名，要追问指标、链路、异常、边界、取舍和个人贡献。
- 候选人的满意回答不需要和本文完全一致，但必须包含场景、指标、架构、异常和取舍。
- 风险回答通常只有名词、组件、宏观描述，没有指标口径和生产边界。

## 4. 推荐面试流程

### 4.1 60 分钟版本

| 时间 | 环节 | 目标 |
| --- | --- | --- |
| 5 分钟 | 自我介绍 | 要求聚焦最近 3 年最核心项目 |
| 15 分钟 | 项目架构图 | 选择一个核心项目画架构图，追问关键链路和本人贡献 |
| 20 分钟 | 核心方向深挖 | 推荐系统、全链路灰度、消息一致性、RAG 四选二或选四 |
| 15 分钟 | 系统设计或代码题 | 全链路灰度、推荐服务、滑动窗口限流器三选一 |
| 5 分钟 | 事故与复盘 | 看风险意识、复盘能力、团队协作和技术判断 |

开场问题：

> 请你选择最近 3 年最熟悉、最能代表你技术和项目管理能力的一个项目，用 5 分钟讲清楚业务目标、团队分工、你本人职责、关键指标和最终结果。

收口问题：

> 如果这个项目重新做一次，你会保留什么设计，推翻什么设计？为什么？

### 4.2 90 分钟版本

如果时间更充裕，建议增加：

- 10 分钟：现场白板设计全链路灰度或推荐服务。
- 10 分钟：代码题，验证是否仍有一线编码能力。
- 10 分钟：项目管理压力测试，验证资源冲突、延期、质量风险下的处理方式。

## 6. 核心主线一：推荐系统与流量策略

### 6.1 简历依据

候选人在搜款网担任高级技术经理，负责大数据、算法、流量策略团队，主导算法推荐架构云端迁移。简历中写到：

- 人均分发提升 200%+。
- 广告 ARPU 提升 50%+。
- 规范用户行为埋点，保障行为归因准确率。
- 主导策略中台建设，SLA >= 99.99%。

### 6.2 基础必备知识

推荐系统通常是一条链路，不是单个模型：

1. 用户行为采集：曝光、点击、收藏、购买、停留。
2. 用户画像与商品特征生产。
3. 多路召回：热门、协同过滤、向量召回、规则召回等。
4. 粗排、精排、重排。
5. 业务规则融合：广告、库存、价格、商家权重、多样性。
6. A/B 实验验证效果。
7. 线上监控、超时、降级、兜底。

常见指标：

- CTR：点击率。
- CVR：转化率。
- GMV：交易额。
- ARPU：平均每用户收入。
- 人均分发：需要候选人自己定义清楚。
- 曝光、点击、下单、成交、留存。

### 6.3 主问题

> 你简历里写人均分发提升 200%+，广告 ARPU 提升 50%+，请你讲清楚这两个指标的定义、实验设计、推荐链路改造，以及如何证明收益来自推荐系统。

### 6.4 参考回答应包含

满意回答应大致包含：

- 指标口径：人均分发不是简单曝光量，要说明分子、分母、有效分发定义；广告 ARPU 是广告收入除以活跃用户数，或候选人所在业务真实口径。
- 实验设计：按用户或商家稳定分桶，实验组走新推荐链路，对照组保持旧策略。
- 归因控制：排除大促、流量来源变化、类目变化、广告库存变化、季节因素。
- 技术链路：召回扩展、实时行为特征接入、排序模型优化、重排策略调整、埋点规范。
- 线上可用：有延迟预算、缓存、热门商品兜底、规则兜底、模型服务超时降级。
- 本人贡献：候选人本人负责架构、策略中台、团队推进、核心链路设计中的哪一部分。

### 6.5 深挖点

- 召回、粗排、精排、重排分别怎么做？
- 用户画像、商品特征、实时行为特征分别如何生产和更新？
- 埋点缺失、重复、延迟如何发现？
- 模型离线效果好，但线上转化变差，如何排查？
- CTR、CVR、GMV、ARPU、留存冲突时如何取舍？
- 冷启动用户和冷启动商品怎么处理？
- 推荐服务 P99 延迟预算是多少？
- SLA 99.99% 如何做到？故障预算是多少？

### 6.6 压力测试

- 如果大促当天模型服务超时率突然升高，你怎么止血？
- 如果实验组 ARPU 提升，但用户留存下降，你怎么决策？
- 如果产品要求强插高佣商品，算法指标会下降，你如何沟通？
- 如果埋点发现过去一个月点击数据重复上报，你怎么修复模型和报表？
- 如果老板要求把 200% 提升写进 OKR，你如何证明这个数字经得起审计？

### 6.7 好信号与风险信号

好信号：

- 能讲清指标口径、A/B 实验、特征链路、召回排序分层、线上降级。
- 能区分推荐收益、广告策略收益、活动收益、流量结构变化。
- 能说明自己在策略、架构、团队推进中的具体贡献。

风险信号：

- 只说换了深度学习模型，所以提升很多。
- 只有提升百分比，没有实验和口径。
- 讲不清用户行为数据如何进入模型。
- 讲不出线上超时、降级、兜底。

## 7. 核心主线二：RAG 与多模态图文匹配 Agent

### 7.1 简历依据

候选人在搜款网建设过基于 RAG 的多模态图文匹配 Agent 系统，技能中包含 Faiss、RAG、语义检索、Dify。

### 7.2 基础必备知识

RAG 可以理解为“先检索，再基于检索结果生成或判断”。典型链路：

1. 文本或图片向量化，也就是 embedding。
2. 向量写入向量库，例如 Faiss。
3. 用户 query 或待匹配对象向量化。
4. 用相似度召回候选内容。
5. 用 rerank 模型或业务规则重排。
6. 将证据和上下文提供给大模型。
7. 输出结果并控制幻觉。

多模态图文匹配还要处理：

- 图片向量和文本向量是否处在同一语义空间。
- 图片标题、描述、类目、属性如何融合。
- 召回准确率和线上业务指标如何评估。
- 索引增量更新、删除、重建如何处理。

### 7.3 主问题

> 你们的多模态图文匹配 RAG 系统解决什么业务问题？图片和文本是怎么检索到一起的？如何评估效果？

### 7.4 参考回答应包含

满意回答应大致包含：

- 业务问题：例如商品图文匹配、相似商品识别、素材审核、商品理解或搜索召回。
- 向量化：图片侧抽取视觉特征，文本侧处理标题、描述、类目、属性；可能使用多模态 embedding 映射到同一语义空间，也可能分别召回后融合。
- 检索：Faiss 做向量索引，根据数据量、延迟、召回率选择 Flat、IVF、HNSW、PQ 等索引。
- 重排：召回后用 rerank，结合类目、属性、相似度、业务规则。
- 评估：人工标注集、Precision、Recall、NDCG，以及线上点击、转化、审核通过率。
- 幻觉控制：控制上下文来源、引用证据、置信度阈值、低置信拒答。
- 工程问题：增量更新、删除、重建索引、数据质量、反馈闭环。

### 7.5 深挖点

- 用的是什么 embedding 模型？为什么选它？
- 图文在同一向量空间，还是分开召回后融合？
- 正负样本如何构建？
- Faiss 索引如何选型？
- 向量召回结果相关性差，排查路径是什么？
- Agent 工具调用边界怎么控制？
- 如何避免无限循环或错误调用？
- Dify 在里面承担编排、知识库还是应用层角色？

### 7.6 压力测试

- 如果向量召回 Top10 全都不相关，你从数据、模型、索引、query 四层怎么排查？
- 如果业务要求 100ms 内返回，但 rerank 很慢，你怎么取舍？
- 如果商品图很好但标题很差，图文融合如何设计？
- 如果模型输出“看起来合理但没有依据”的结果，线上怎么拦截？
- 如果索引每天更新百万级商品，如何保证增量更新不影响查询？

### 7.7 好信号与风险信号

好信号：

- 能讲 embedding、索引、召回、rerank、评估集、线上反馈闭环。
- 知道 RAG 不是把资料丢给大模型。
- 能讲清业务指标和工程约束。

风险信号：

- 只说“大模型加知识库”。
- 不懂向量索引和召回评估。
- 不知道如何处理幻觉、低置信和索引更新。

## 8. 核心主线三：服务化框架与全链路灰度

### 8.1 简历依据

候选人在货拉拉基础设施部门主导并支持泛服务化调用框架，设计熔断、降级、限流、注册中心、高可用和全链路灰度能力。

### 8.2 基础必备知识

服务治理解决微服务系统中的稳定性和可控性问题：

- 注册发现：服务实例如何被找到。
- 熔断：下游持续失败时暂时停止调用。
- 限流：限制请求量，保护系统。
- 降级：非核心能力失败时返回兜底结果。
- 灰度：让少量用户、租户或流量先走新版本。
- 链路追踪：知道一次请求经过哪些服务。

全链路灰度的难点：

- 灰度标识从入口一路传递到下游。
- HTTP、RPC、MQ 都要透传灰度上下文。
- 灰度流量不能错误进入普通实例。
- 普通流量不能误入灰度实例。
- 需要监控、报警、一键回滚和污染检测。

### 8.3 主问题

> 全链路灰度具体怎么做？如果一个灰度请求经过 HTTP、RPC、MQ，怎么保证后续链路都走灰度环境？

### 8.4 参考回答应包含

满意回答应大致包含：

- 入口打标：网关根据用户、城市、租户、版本、请求头等规则判断是否命中灰度，并写入 header 或 trace context。
- 上下文透传：RPC 框架自动透传灰度标识，避免业务代码手写。
- 服务路由：服务发现或负载均衡根据灰度标识选择灰度实例。
- MQ 链路：生产者把灰度标识写入 message header，消费者按标识路由到灰度处理逻辑或灰度实例。
- 污染检测：监控灰度请求是否调用了非灰度实例，普通请求是否误入灰度实例。
- 回滚能力：灰度规则动态刷新、一键关闭、兜底路由、审计。
- 框架治理：SDK 版本兼容、老业务迁移、规则优先级、缓存刷新。

### 8.5 深挖点

- 泛服务化调用框架的核心抽象是什么？
- 接口、路由、协议、序列化如何设计？
- 注册中心如何保证高可用？
- 服务发现缓存失效怎么办？
- 灰度规则冲突时如何处理优先级？
- 限流是单机限流还是分布式限流？
- 令牌桶和漏桶有什么差异？
- 限流策略误伤核心客户时如何快速恢复？
- SDK 升级如何兼容旧业务？

### 8.6 压力测试

- 如果灰度请求调用了普通服务，会造成什么后果？如何发现？
- 如果 MQ 消息丢失灰度标识，如何补救？
- 如果注册中心短暂不可用，新实例上线和老实例下线会发生什么？

## 15. 代码题：滑动窗口限流器

### 15.1 题目

实现一个单机版滑动窗口限流器，并说明如何扩展成 Redis 分布式版。

```java
boolean allow(String key, int limit, long windowMillis)
```

功能要求：

- 同一个 key 在窗口内最多允许 limit 次。
- 考虑并发安全。
- 说明单机版如何扩展到 Redis 分布式版。

### 15.2 基础必备知识

常见限流算法：

- 固定窗口：实现简单，但窗口边界可能瞬间放过两倍流量。
- 滑动日志：记录每次请求时间，精确但内存成本较高。
- 滑动窗口计数：把窗口拆成多个小格，精度和成本折中。
- 令牌桶：允许一定突发流量。
- 漏桶：让请求以固定速度流出。

### 15.3 参考回答

单机版可接受思路：

```java
public class SlidingWindowLimiter {
    private final ConcurrentHashMap<String, Deque<Long>> records = new ConcurrentHashMap<>();

    public boolean allow(String key, int limit, long windowMillis) {
        long now = System.currentTimeMillis();
        Deque<Long> queue = records.computeIfAbsent(key, k -> new ArrayDeque<Long>());
        synchronized (queue) {
            while (!queue.isEmpty() && now - queue.peekFirst() >= windowMillis) {
                queue.pollFirst();
            }
            if (queue.size() >= limit) {
                return false;
            }
            queue.addLast(now);
            return true;
        }
    }
}
```

这个答案的优点：

- 用 `ConcurrentHashMap` 管理不同 key。
- 对单个 key 的队列加锁，避免全局锁。
- 每次请求清理窗口外时间戳。
- 逻辑简单，能说明滑动日志算法。

Redis 分布式版满意回答：

> 可以用 Redis ZSet 实现。key 是限流对象，score 和 member 包含当前时间戳和随机值。每次请求先删除窗口外数据，再统计窗口内数量，如果小于 limit 就写入当前请求并允许，否则拒绝。整个过程用 Lua 脚本保证原子性。时间最好使用 Redis 服务器时间，避免应用机器时钟不一致。还要给 key 设置过期时间，防止内存泄漏。

### 15.4 深挖点

- 固定窗口有什么问题？
- 滑动日志和滑动计数器有什么区别？
- key 很多时，空队列如何清理？
- 单个热 key 并发很高怎么办？
- 系统时间回拨怎么办？
- limit 或 windowMillis 非法怎么办？
- Redis ZSet 热 key 如何优化？

### 15.5 压力测试

- 如果一个 key 每秒 10 万请求，队列锁会不会成为瓶颈？
- 如果机器时间突然回拨 1 分钟，限流逻辑会发生什么？
- 如果 Redis 网络抖动，是放行、拒绝还是降级成本地限流？
- 如果 key 无限增长，如何避免内存泄漏？

### 15.6 评分要点

- 5 分：代码正确、并发安全、边界清楚，能讲 Redis Lua、服务器时间、过期、热 key。
- 4 分：单机代码基本正确，Redis 扩展思路完整。
- 3 分：思路对，但并发或边界处理有明显遗漏。
- 1-2 分：无法写出可运行结构，或不知道分布式原子性问题。

## 16. 项目管理与领导力问题

### 16.1 项目 owner 能力

主问题：

> 飞书 eLearning team size 约 20，你作为项目 owner，如何拆阶段、控风险、做技术选型，并协调产品、业务方和研发团队？

参考回答应包含：

- 明确业务目标和 MVP。
- 拆分里程碑和验收标准。
- 技术选型有调研、评估、风险列表。
- 跨团队沟通有机制，不靠临时救火。
- 上线前有灰度、监控、回滚和风险预案。
- 上线后有复盘和长期治理。

深挖点：

- 最大资源冲突是什么？
- 哪个需求被砍掉或延期？为什么？
- 哪次技术选型后来证明错了？
- 如何保证 20 人团队代码质量一致？

压力测试：

- 如果业务要求两周上线，但你判断架构风险很高，你怎么处理？
- 如果产品、算法、后端对优先级各执一词，你怎么推动决策？
- 如果核心成员离职，项目如何继续？

### 16.2 团队搭建与人员培养

主问题：

> 你从 0 搭建成都技术团队时，前 3 个月具体做了什么？如何保证交付和团队成长同时发生？

参考回答应包含：

- 明确团队职责边界和近期目标。
- 建立研发流程、技术评审、代码评审、上线规范。
- 根据能力分配模块，并设置 mentor。
- 通过文档、分享、复盘沉淀团队能力。
- 用可度量指标看交付质量和协作效率。

深挖点：

- 如何判断一个人适合放在哪个模块？
- 如何培养初中级工程师？
- 如何处理团队成员能力差异？
- 如何防止架构设计和最终实现脱节？

压力测试：

- 如果团队连续延期两次，你如何定位是人、流程、目标还是技术债问题？
- 如果一个技术骨干很强但协作很差，你怎么处理？
- 如果上级只看短期交付，你如何争取技术治理时间？

## 17. 线上故障与技术决策

### 17.1 主问题

- 你最近一次线上事故是什么？根因、止血、复盘、长期修复分别是什么？
- 你做架构选型时，最近一次推翻自己原方案是什么？
- 你现在还会亲自写核心代码吗？最近写过的最复杂模块是什么？
- 如果重新做一次某个核心项目，你会改哪里？

### 17.2 参考回答应包含

满意回答不一定要事故很大，但应包含：

- 事故现象：用户影响、错误率、延迟、数据影响。
- 止血动作：回滚、降级、限流、扩容、切流。
- 根因分析：技术根因和流程根因。
- 长期修复：监控、报警、测试、评审、自动化、预案。
- 个人反思：自己当时判断哪里不足。

### 17.3 好信号与风险信号

好信号：

- 坦诚讲问题，不甩锅。
- 能区分止血、修复、复盘和机制建设。
- 能讲自己做过的错误决策和后续调整。

风险信号：

- 说没有事故。
- 全部归因给别人或外部系统。
- 只讲修了 bug，没有复盘机制。

## 18. 通用深挖模板

当候选人讲任何一个复杂项目时，都可以按下面顺序追问：

| 层次 | 问法 | 判断目的 |
| --- | --- | --- |
| 背景 | 这个项目为什么做？不做会怎样？ | 看业务理解 |
| 指标 | 成功指标是什么？分子分母是什么？ | 看数据意识 |
| 角色 | 你本人负责哪部分？哪些是你拍板的？ | 看真实性 |
| 架构 | 画一下核心链路和模块边界 | 看架构能力 |
| 细节 | 状态机、数据结构、异常路径是什么？ | 看一线能力 |
| 取舍 | 为什么不用另一个方案？缺点是什么？ | 看技术判断 |
| 线上 | 如何监控、降级、回滚、复盘？ | 看工程落地 |
| 管理 | 如何拆阶段、协调资源、处理冲突？ | 看项目能力 |

万能压力问题：

- 如果流量放大 10 倍，哪里先挂？
- 如果下游服务不可用 30 分钟，系统怎么表现？
- 如果数据重复、延迟、丢失，你怎么处理？
- 如果上线后核心指标反而下降，你怎么排查？
- 如果核心成员离职，项目风险如何控制？
- 如果重新做一次，你会删掉什么设计？

## 19. 打分评价表

建议按 5 分制评分，每项单独打分，最后给综合结论。

| 维度 | 1-2 分 | 3 分 | 4 分 | 5 分 |
| --- | --- | --- | --- | --- |
| 技术真实性 | 讲不清本人贡献，指标含糊 | 项目大体真实，但细节不稳 | 能讲清关键链路和个人贡献 | 多项目细节扎实，可交叉验证 |
| 架构能力 | 组件堆砌，无取舍 | 能画大体架构 | 模块边界、扩展性、可用性清楚 | 能从业务目标推导架构并讲成本 |
| 工程落地 | 忽略异常和线上风险 | 有基本监控和重试意识 | 有降级、幂等、回滚、补偿 | 对故障、数据、性能、可观测性很完整 |
| 一线编码 | 无法写出基本代码 | 思路有但边界弱 | 能写正确代码并说明并发 | 代码、边界、分布式扩展都扎实 |
| 数据意识 | 只有结果数字 | 能解释部分指标 | 能讲实验和归因 | 指标口径、显著性、冲突取舍都清楚 |
| 项目管理 | 只讲自己做技术 | 能描述协作过程 | 能讲拆解、里程碑、风险 | 能建立机制并带团队稳定交付 |
| 复盘能力 | 回避事故或甩锅 | 能讲修复 | 能讲根因和长期修复 | 能把事故转成机制和团队能力 |

### 19.1 综合结论建议

强通过：

- 能深讲 2 到 3 个核心项目。
- 指标、架构、异常、取舍、个人贡献都扎实。
- 仍具备一线技术判断力。
- 能带团队交付复杂项目。

通过：

- 项目经验真实，部分方向深度略弱。
- 能胜任架构负责人或技术负责人角色。
- 需要在二面进一步验证管理或编码短板。

待定：

- 管理表达较强，但关键技术细节不稳。
- 指标口径或本人贡献有模糊点。
- 建议二面指定一个项目连续深挖，或加现场代码题。

不通过：

- 简历中的核心指标经不起追问。
- 无法解释核心方案、异常处理和个人贡献。
- 大量回答停留在组件名和宏观描述。

## 20. 推荐面试组合

如果时间有限，最推荐执行下面组合：

1. 推荐系统收益：验证业务指标、推荐链路和真实性。
2. 全链路灰度：验证基础架构深度和工程治理。
3. 消息一致性：验证生产级落地能力。
4. 滑动窗口限流代码题：验证一线编码能力。
5. 项目 owner 压力测试：验证资源协调、风险控制和复盘能力。

这组组合可以较快区分三类候选人：

- 真正做过复杂项目的人。
- 只参与过项目但包装成主导的人。
- 管理表达强但技术细节已经脱离一线的人。
